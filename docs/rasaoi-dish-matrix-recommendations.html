01 Short answers

QuestionPlain answer
1. Vague prompt → same outcomes? High confusion risk when the Ask is mood-only and the local menus are thin or similar. Not “AI broken” — soft dials + weak catalog signal.
2. Go fully to Database? Large win for freshness, payload, and phone speed. Medium only for vague-Ask variety unless you also add tags + score math. Does not fix bad named-dish match rules by itself.
3. Many sequential tables? Do not build a mandatory join chain (location→gender→health→…→dish). Use hard gates + soft tags on live dishes instead.
4. Named dish → correct hero? Not guaranteed today — soft token F() can crown Butter Dosai for “Butter chicken.” Fix match rules (P0) before celebrating math moves.
Keep forever: real menus only, catalog plate gate, sanitize after AI, Ask-fulfillment first with honest F(), Lab promote gate, no clinical over-claims.

02 Q1 — Vague prompts & “same” results

When someone says “something nice” or only moves mood dials, the system has little hard signal. Dials sit near the middle. Many EDH/Folsom kitchens share similar North Indian staples. Ranking then leans on soft vibe math — so Readings look alike.

Why it feels the same (today)

Ask side

Vague text → default dials. Few filters. No named dish, protein, or exclusion. Soft scores dominate.

Catalog side

Overlapping menus. Identity enrich improved (proteins/diet ~100% post ROE-022); cuisine_region ~30%, gi_band ~0% remain. Match-rule holes still allow soft F() false positives.

Vague Ask ──► dials ≈ mid ──► soft score J_soft │ thin / similar menus │ ▼ Same top kitchens · same staples Best / Clean / Heritage converge Sharp Ask (“goat, not chicken”) ──► exclude + protein ▼ Ask-fulfillment separates kitchens (when identity fires) Named Ask (“butter chicken”) ──► token F() today ▼ Partial on “butter” alone → wrong hero possible
Important: “Results say the same” is often catalog poverty + soft ranking, not a broken model. Separately, named-dish false heroes are match-rule debt (§3b) — not fixed by inventing plates or by J weights alone.

05 Q3 — Sequential tables: opinion

The sketch (Ask → location → event → gender → user type → health → ethic → diet → macro → therapeutic → dish) is a useful thinking list. As a literal SQL join pipeline, it is a poor fit for Rasaoi.

Why not a 10-step join chain

ProblemWhat goes wrong
Most Asks omit stages Gender, age, renal, DASH rarely said. Empty stages = noise and ops cost.
Hard AND filters shrink Eligible Too many gates → empty set → same fallbacks / “no match” loops (more sameness).
Gender / age as dish filters EDH menus are not tagged this way; product and fairness risk if forced as hard gates.
Clinical health tables “Diseased / renal / pregnant” as ranked DB paths invites medical claims. Handbook: wellness, not clinical.
One mega-column table Brittle migrations; every new diet flag becomes a column war.
Recommendation: treat the sketch as a dimension checklist, not as a mandatory pipeline of tables in the hot path.

06 Recommended model (hard gates + soft tags)

Keep the Outcome Engine path simple. Split must-pass from nice-to-rank.

Eligible then rank (same idea as upgrade J) Eligible = dishes/kitchens that pass diet ∩ ethic ∩ exclude ∩ regional ∩ catalog ∩ named-Ask F policy
Maximize J = w_F·F + w_D·D + w_P·P + w_B·B + w_W·W − w_G·G
Soft tags change weights — they do not override a failed named-dish / protein gate (Rev 1.1 R1–R5).

Data shape (lean)

dishes / culinary knowledge (live rows) │ └── dish_tags (dish_id, dimension, tag, speculation_tier) dimension ∈ { diet, ethic, macro, wellness, therapeutic, allergen, food_type, … } Optional profile (prefs only): location · household (kid/adult) · default occasion Bio / clinical raw signals stay on-device / caveated Not recommended: gender_only table as hard dish filter; “diseased” as a ranked therapeutic table without legal copy
LayerExamplesBehavior
Hard gates Jain, vegan, halal, allergy excludes, catalog membership, named-Ask protein/F policy (R1–R5) Fail → out or Closest-capped. No soft override to naked 100%.
Soft score Celebration dial, light/fresh tags, keto-ish, purity, budget, GL lens Reorder Eligible; never invent dishes.
Profile prefs EDH/Folsom, family night, prefer veg Defaults for parse — user Ask still wins.

08 Phased advice — Rev 1.1

  1. P0 — Named-dish / F() match rules — implement audit M-01…M-06 / rules R1–R6; Vitest soak Butter chicken, Mysore pak, ghee roast. Blocks false 100% heroes.
  2. Maintain identity + alias parity — ROE-022 raised proteins/diet; finish cuisine_region / food_type; keep culinary:check-aliases green.
  3. Live culinary in Postgres + score-reading — freshness and phone speed (combined proposal). Carry fixed F() into Edge. Keep Lab gate.
  4. Tag model — dish_tags for ethic / diet / macro / wellness / therapeutic with speculation_tier. Hard vs soft rules in one place.
  5. Vague-Ask UX — Pareto plates + alternate diversity; show “why” bars; honest Closest when catalog is thin or match is weak.
  6. Defer — gender hard-gates; clinical therapeutic ranking until data + legal copy exist.
Do nowP0 match rules · soak pack · keep enrich/aliases
Do nextLive DB cache · score-reading (with fixed F)
Do with careTags · GL · therapeutic caveats
Don’t10-table AND · invent plates · math-before-match
Bottom line: fix sameness with better real choices + clearer gates + soft ranking math. Fix named-dish false heroes with honest F() first. Move cognition to the Database for speed and freshness — encode the checklist as tags and weights, not a long forced join.
